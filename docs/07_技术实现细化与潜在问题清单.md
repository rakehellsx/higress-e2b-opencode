# 类 Manus 智能体平台：技术实现细化与潜在问题清单

## 1. 引言

在现有《平台架构调研报告》《多租户隔离与资源配额管理方案》《计费系统集成设计方案》以及《模块功能详细说明与串联关系》的基础上，本文进一步补充平台从“架构蓝图”走向“可实现系统”时需要落地的关键技术细节、接口边界、状态模型和潜在问题。本文的目标不是重复已有结论，而是把此前偏概念化的设计，细化成更接近工程实施的方案，并对高风险环节进行前置暴露和缓解建议。

从整体上看，该平台不是单一的 Agent 应用，而是一个由 **任务编排、沙箱执行、模型网关、MCP 工具接入、实时计量、配额控制和账单结算** 共同组成的企业级控制系统。其真正难点不在于单点能力，而在于全链路的一致性、可观测性和补偿能力。因此，后续实现必须优先围绕 **上下文传播、状态机设计、事件账本、幂等写入、权限边界和失败补偿** 来组织系统，而不是只围绕“模型调用是否成功”来做功能开发。

## 2. 建议补齐的总体技术原则

在落地阶段，建议将平台设计约束收敛为以下六项原则。

| 原则 | 说明 | 工程含义 |
| :--- | :--- | :--- |
| **统一上下文** | 每个请求都必须携带 `tenant_id`、`user_id`、`task_id`、`session_id`、`trace_id` | 所有日志、事件、计量、权限校验必须围绕统一上下文展开 |
| **事件优先** | 状态变化以事件为主，而不是靠轮询拼接事实 | 任务状态、计量状态、账单状态都需要事件账本 |
| **幂等补偿** | 允许重复投递，但不允许重复记账与重复执行 | 对 Webhook、重试队列、账单推送均要设计幂等键 |
| **权限最小化** | Agent 能调用的模型、工具、命令、网络范围必须收敛 | 工具调用需要授权层，而不只是代码里 if 判断 |
| **读写分离** | 在线控制路径与离线对账路径必须分离 | 防止实时任务链路被计费计算或 BI 查询拖慢 |
| **可回放** | 任一任务都应可重建关键过程 | 便于审计、追责、故障排查和账单争议处理 |

如果没有这些原则，平台很容易出现“架构图看起来完整，但系统一旦出现重试、超时、暂停恢复、跨租户并发时就失控”的问题。

## 3. 控制面的服务拆分建议

现有文档把“平台后端”描述为一个统一实体，但真正实施时，建议至少拆成下述服务，以降低单服务复杂度和故障耦合。

| 服务 | 核心职责 | 推荐技术形态 |
| :--- | :--- | :--- |
| **API Gateway / BFF** | 接收前端请求、用户鉴权、参数校验、输出聚合 | FastAPI / NestJS |
| **Task Orchestrator** | 创建任务、分配资源、驱动任务状态机、管理重试 | FastAPI + PostgreSQL + Redis |
| **Sandbox Manager** | 封装 E2B SDK、模板管理、生命周期管理、快照恢复 | Python service |
| **Agent Session Service** | 负责 OpenCode Session 创建、Prompt 注入、事件订阅、消息归档 | Python / TS service |
| **Metering Ingestor** | 接收 Higress 与 E2B 事件，做验签、去重、规范化 | Python / Go |
| **Billing Worker** | 对接 OpenMeter / Stripe，执行对账、出账、补偿和通知 | Async worker |
| **Notification Service** | 邮件、Webhook、站内通知、余额预警 | Worker / queue consumer |

这种拆分的好处在于：控制面不需要把“同步 API 返回”和“长任务编排”“异步计费”“告警通知”强行塞进一个进程里。特别是 Metering 与 Billing，应该天然与在线任务执行解耦，否则一旦账单或 OpenMeter 出现抖动，就会反过来影响任务调度。

## 4. 统一上下文与状态模型

### 4.1 统一标识设计

建议在数据库和事件层统一引入如下核心标识。

| 字段 | 用途 | 来源 |
| :--- | :--- | :--- |
| `tenant_id` | 多租户隔离与计费主体 | 平台租户系统 |
| `user_id` | 操作发起者 | 用户中心 / IAM |
| `task_id` | 一次用户任务实例 | Task Orchestrator |
| `session_id` | OpenCode 会话主键 | Agent Session Service |
| `sandbox_id` | E2B 沙箱标识 | E2B API |
| `trace_id` | 跨服务追踪 ID | API Gateway 生成并透传 |
| `billing_subject_id` | 计费主体，允许和租户不同 | Billing 域模型 |
| `event_id` | 每条事件的唯一编号 | 各事件源或接入层生成 |

特别需要强调的是，**`task_id`、`session_id` 与 `sandbox_id` 不能互相混用**。用户看到的是任务；Agent 运行的是会话；基础设施管理的是沙箱。三者一旦混淆，会直接导致日志关联困难、恢复逻辑出错和计费口径失真。

### 4.2 任务状态机建议

平台应显式定义任务状态机，而不是把状态当普通字符串字段使用。

| 状态 | 含义 | 允许迁移 |
| :--- | :--- | :--- |
| `PENDING` | 任务已创建但尚未分配资源 | `PRECHECKING`、`CANCELLED` |
| `PRECHECKING` | 做余额、权限、配额和参数检查 | `ALLOCATING`、`FAILED_PRECHECK` |
| `ALLOCATING` | 创建沙箱、分配模型/工具资源 | `RUNNING`、`FAILED_ALLOCATE` |
| `RUNNING` | Agent 正在执行 | `WAITING_USER`、`PAUSED`、`SUCCEEDED`、`FAILED_RUNTIME` |
| `WAITING_USER` | 需要人工介入，如验证码、二次确认 | `RUNNING`、`TIMEOUT`、`CANCELLED` |
| `PAUSED` | 沙箱或任务被显式暂停 | `RUNNING`、`EXPIRED` |
| `SUCCEEDED` | 正常完成 | 无 |
| `FAILED_*` | 各类失败终态 | 可允许人工 `RETRYING` |
| `CANCELLED` | 主动取消 | 无 |
| `TIMEOUT` | 超时终止 | 无 |

如果任务状态机不严格，后续就会很难回答“为什么用户被扣费但任务显示失败”“为什么沙箱已经销毁但前端还显示运行中”这类真实问题。

## 5. Higress 网关层的实施细化

Higress 在本方案中不只是流量入口，更是模型治理、MCP 工具接入、租户身份映射和在线配额控制的核心枢纽。根据 Higress 官方文档，`ai-token-ratelimit` 插件基于 Redis 做 Token 级限流，并支持基于 Consumer、Header、Param、Cookie、IP 等动态键进行差异化控制 [1]。因此，在平台实施时，建议围绕“消费者建模—路由策略—插件编排—异常退化”四个维度补齐细节。

### 5.1 Consumer 与鉴权建模

建议将租户、应用和用户 Token 三个层级拆开建模，而不是只用一个 API Key 覆盖全部场景。

| 层级 | 用途 | 建议凭证 |
| :--- | :--- | :--- |
| **Tenant Consumer** | 计费、额度、全局速率限制 | API Key / JWT |
| **App Consumer** | 同租户下不同业务系统的流量隔离 | 子级 API Key |
| **User Session Token** | 前端登录与操作行为归属 | JWT / OIDC token |

较稳妥的做法是：前端用户先通过平台身份系统获取 JWT，后端再将租户上下文映射到调用 Higress 的内部 Consumer 身份。这样可以避免把网关 Consumer 直接暴露给最终用户，同时保留细粒度审计能力。

### 5.2 路由与降级策略

模型网关层至少需要支持如下路由策略。

| 策略 | 说明 |
| :--- | :--- |
| **主模型 + 备用模型** | 例如主用高性能模型，超时或熔断时降级到次级模型 |
| **按租户套餐路由** | 企业高级版可走更高成本模型，基础版走性价比模型 |
| **按任务类型路由** | 代码类、搜索类、推理类分别走不同模型 |
| **按地区或合规域路由** | 对敏感租户使用私有化或指定区域模型提供商 |

这里的风险在于：如果前端任务类型分类、后端策略引擎和 Higress 路由规则之间没有统一枚举，就会出现“前端说是代码任务，网关按通用聊天任务路由”的策略漂移问题。因此建议把模型策略抽象成独立的 **Model Policy Registry**，由后端和网关共用。

### 5.3 插件编排顺序建议

建议网关插件执行顺序遵循“鉴权 → 配额检查 → 限流 → 安全检查 → 模型调用 → 统计上报”的链路。若先做模型调用后做统计，会丢掉拦截前的信息；若先做限流后做鉴权，则会无法形成按消费者维度的准确限流。

### 5.4 可能的问题

Higress 层最容易出现的问题不是功能没有，而是数据口径和缓存/限流策略不一致。例如：

1. Redis 故障会直接影响 `ai-token-ratelimit` 的判断，若没有 fail-open / fail-close 策略，可能出现全量放行或全量拒绝。
2. 语义缓存若未纳入计费口径，会出现用户认为“命中缓存也被扣费”的争议。
3. Fallback 模型切换若不回写任务事件，会导致账单显示主模型、实际却走了备用模型。
4. MCP 代理若不区分租户上下文和工具作用域，可能造成跨租户工具误调用。

## 6. OpenCode 运行时与调度实现细化

根据 OpenCode SDK 文档，OpenCode 提供 JS/TS SDK、Session API、Shell API 以及 SSE 事件订阅能力，支持通过已有 server 实例或 SDK 启动本地 server 后进行程序化控制 [2]。这意味着平台在设计上不应只把 OpenCode 当命令行程序使用，而应把它当作一个 **会话型 Agent Runtime** 来管理。

### 6.1 会话初始化流程

建议每次任务启动时执行如下初始化顺序：

1. 在 Task Orchestrator 中创建任务记录；
2. 由 Sandbox Manager 拉起 E2B 沙箱；
3. 在沙箱内启动 OpenCode server；
4. Agent Session Service 创建 `session_id`；
5. 注入系统 Prompt、租户上下文、可用工具清单、模型策略；
6. 建立 SSE 事件订阅，开始接收消息、状态和工具调用事件；
7. 再向会话发出正式任务 Prompt。

如果在 SSE 订阅建立之前就先下发任务，很容易丢掉任务初始阶段最关键的状态事件。

### 6.2 Prompt 注入分层

建议将 Prompt 拆为四层，而不是把所有约束直接拼成一大段文本。

| 层级 | 内容 | 变更频率 |
| :--- | :--- | :--- |
| **System Layer** | 平台全局规则、安全边界、输出协议 | 低 |
| **Tenant Policy Layer** | 租户允许使用的工具、模型、域名、预算 | 中 |
| **Task Context Layer** | 本次任务目标、输入资料、文件上下文 | 高 |
| **Interaction Layer** | 用户追问、纠偏、人工接管信息 | 高频 |

这样做的好处是便于缓存、复用、差异化审计和上下文裁剪。如果所有内容都以单次 Prompt 字符串注入，会严重影响长任务稳定性，也不利于后续做会话恢复。

### 6.3 工具调用授权模型

建议平台不要默认允许 Agent 访问所有 MCP 工具，而是引入 **Tool Grant** 模型。

| 授权维度 | 示例 |
| :--- | :--- |
| 按租户 | 某租户可用 Jira、Confluence，不可用 GitHub Admin |
| 按任务类型 | 仅代码审查任务可调用 Git 仓库写接口 |
| 按运行阶段 | 读取阶段允许搜索，提交阶段才允许写入 |
| 按人工确认 | 发帖、付款、删除数据等动作必须人工确认 |

如果没有这一层授权，Agent Runtime 很可能演变成“谁拿到任务都能默认调用全部工具”的高风险系统。

### 6.4 可能的问题

OpenCode 侧的高频问题主要包括：

1. **上下文膨胀**：长任务、多轮追问和大文件分析会让上下文迅速变大，必须有消息摘要与裁剪策略。
2. **会话漂移**：同一会话内多次追问若未固化阶段结果，Agent 可能偏离原任务目标。
3. **工具震荡**：模型在失败时反复调用同一工具，导致循环开销和重复计费。
4. **权限等待阻塞**：若权限请求没有统一回调机制，任务会卡在等待人工处理中，且前端难以理解当前状态。

## 7. E2B 沙箱层的实施细化

E2B 提供基于沙箱生命周期的 Webhook 机制，可订阅 `created`、`updated`、`killed`、`paused`、`resumed`、`checkpointed` 等事件，并通过签名头做真实性校验 [3]。这使得平台可以把沙箱从“黑盒运行环境”提升为“可计量、可追踪、可恢复的资源对象”。

### 7.1 模板与镜像管理

建议平台至少维护三类沙箱模板。

| 模板 | 用途 | 预装内容 |
| :--- | :--- | :--- |
| **General Agent** | 通用文本、搜索、轻量脚本任务 | Python、Node、常用 CLI、OpenCode |
| **Dev Agent** | 代码修改、依赖安装、测试运行 | Git、构建链、语言运行时、调试工具 |
| **Browser/Desktop Agent** | 图形界面操作、网页自动化 | 浏览器、桌面环境、VNC/stream 组件 |

如果所有任务都共用一个臃肿模板，会同时带来启动慢、镜像维护复杂、攻击面扩大的问题。

### 7.2 生命周期与持久化策略

建议明确沙箱生命周期和数据保留策略。

| 事件 | 处理建议 |
| :--- | :--- |
| `created` | 写入资源分配事实，开始计时 |
| `paused` | 记录暂停点和最新工作目录快照 |
| `resumed` | 生成新的执行段（execution segment） |
| `checkpointed` | 标记可恢复快照版本 |
| `killed` | 写入最终执行时长，触发结算与清理 |

其中一个关键细节是：**不要只把一个沙箱当作一个连续时长对象**。对于存在暂停/恢复的任务，更合理的方式是把它建模成多个 execution segment，再汇总为总时长。否则账单、任务回放和故障分析都会变得模糊。

### 7.3 网络与数据出口控制

建议把沙箱网络能力做成可配置策略，而不是默认全开。

| 策略档位 | 说明 |
| :--- | :--- |
| **No Egress** | 仅允许访问平台内部必要服务 |
| **Allowlist Egress** | 只允许访问白名单域名，如 GitHub、企业 API |
| **Full Egress with Audit** | 高权限任务可全网访问，但必须保留审计日志 |

对企业客户来说，是否能精确控制沙箱的外网访问，往往比“是否支持跑 bash”更重要。

### 7.4 可能的问题

1. 沙箱暂停后若使用临时文件系统，恢复时可能出现文件缺失。
2. 同一任务若发生沙箱重建，路径、依赖、端口和进程状态可能全部变化。
3. 生命周期事件若丢失或重复投递，会直接污染计量账本。
4. Desktop/Browser 模板的资源成本显著高于 CLI 模板，如未区分套餐将侵蚀毛利。

## 8. 多租户与权限边界的进一步实现

现有方案提出 Schema-per-tenant、RBAC 和 K8s NetworkPolicy，这个方向正确，但仍需补足权限域与资源域的映射关系。

### 8.1 推荐的权限域拆分

| 权限域 | 典型对象 | 示例动作 |
| :--- | :--- | :--- |
| **Control Plane** | 租户、用户、API Key、账单 | 创建租户、查看账单、重置额度 |
| **Execution Plane** | 任务、会话、沙箱、文件 | 启动任务、终止任务、恢复任务 |
| **Tool Plane** | MCP 工具、外部系统连接 | 读取、写入、删除、提交 |
| **Billing Plane** | 余额、套餐、价格项、发票 | 充值、出账、退款、人工调账 |

如果 RBAC 只停留在“管理员/成员”两个粗粒度角色，将难以覆盖企业环境中的运维、财务、安全审核和普通业务用户差异。

### 8.2 数据库隔离建议

对于 MVP，可采用 **Schema-per-tenant + 平台级公共表** 的混合模式；对于大租户，再考虑迁移到专属数据库或 BYOC。原因在于：纯 RLS 更依赖应用层严格带租户条件，而 Schema-per-tenant 对误写和误查更不敏感，但会提高迁移、DDL 管理和报表聚合复杂度。

### 8.3 可能的问题

1. 租户上下文如果只在 HTTP Header 中传递，进入异步任务后容易丢失。
2. 跨租户聚合报表和运营报表若直接连租户库扫描，会带来性能与安全双重风险。
3. 管理员手工调账或任务回放若不区分租户作用域，容易越权访问数据。

## 9. 计量、配额与账单闭环的实施细化

根据 E2B 生命周期 Webhook 和 Higress AI 插件的能力，平台具备构建“Token 消耗 + 沙箱时长”的双维度计量条件 [1] [3]。与此同时，OpenMeter 的 Stripe 集成文档强调，OpenMeter 更适合承载使用量、产品价格、订阅和账单编排，而 Stripe 则负责支付、税务、发票发送和收款 [4]。因此，计费实现中必须清晰划分“技术事实”和“财务事实”。

### 9.1 计量账本建议

建议先落一层平台自己的 **Usage Ledger**，再同步到 OpenMeter。其核心原因是：第三方计量系统适合聚合和出账，但平台仍需要一份可审计、可回放、可修复的原始账本。

| 字段 | 说明 |
| :--- | :--- |
| `usage_event_id` | 幂等主键 |
| `source` | `higress` / `e2b` / `manual_adjustment` |
| `tenant_id` | 计费租户 |
| `task_id` | 对应任务 |
| `session_id` | 对应会话 |
| `sandbox_id` | 对应沙箱 |
| `meter_type` | `llm_input_token` / `llm_output_token` / `sandbox_ms` |
| `quantity` | 使用量数值 |
| `unit_price_snapshot` | 事件入账时价格快照 |
| `billing_status` | `pending` / `rated` / `invoiced` / `reversed` |
| `raw_payload` | 原始事件 JSON |

如果没有这一层 Usage Ledger，而是直接把所有事件塞给 OpenMeter，再从聚合结果回查明细，后续对账和争议处理会非常痛苦。

### 9.2 在线配额与离线出账要分开

建议把配额控制拆成两层：

| 层级 | 目标 | 延迟要求 |
| :--- | :--- | :--- |
| **在线配额检查** | 控制是否允许继续执行任务或继续调模型 | 毫秒级 |
| **离线账单生成** | 月度/周期出账、税费计算、发票投递 | 分钟到小时级 |

在线路径应尽量依赖 Redis/缓存和最近余额快照；离线路径则可依赖 OpenMeter、Stripe 和补偿作业。不要把 Stripe API 是否正常作为在线任务能否执行的前置条件。

### 9.3 退款与补偿策略

企业平台的一个常见盲点，是只设计成功扣费，不设计失败补偿。建议显式定义以下补偿场景：

1. 模型返回 5xx，但网关已记录输入 Token。
2. 沙箱创建失败，但任务已进入 `ALLOCATING` 且预扣额度已完成。
3. OpenMeter 或 Stripe 暂时不可用，导致账单推送中断。
4. 用户申诉任务结果异常，需要人工豁免或部分退还。

### 9.4 可能的问题

1. 同一任务若调用多个模型，价格快照不固化会导致历史账单不可重算。
2. 不同来源事件延迟不同，可能出现任务结束但账单尚未齐全的短暂不一致。
3. 积分与月结并存时，若扣减顺序不明确，会出现对账分歧。
4. 多币种、税率、发票抬头和法人实体问题在国际化场景中会迅速复杂化。

## 10. 观测性、审计与运维补充

建议将观测性划分为四层，而不是只收集基础 CPU/内存指标。

| 观测层 | 核心问题 | 建议指标 |
| :--- | :--- | :--- |
| **请求层** | 请求是否被正确鉴权、限流、路由 | QPS、429、路由命中率、网关延迟 |
| **任务层** | 任务在哪个阶段失败 | 状态迁移耗时、等待人工比例、重试率 |
| **会话层** | Agent 是否陷入震荡或上下文膨胀 | 工具调用次数、上下文长度、单任务 Token |
| **计费层** | 计量和账单是否一致 | usage backlog、未出账事件数、推票失败率 |

对于审计，建议至少保留以下审计对象：任务输入摘要、系统 Prompt 版本、工具调用记录、模型调用摘要、人工确认记录、账单调整记录。真正面向企业交付时，审计链路的重要性不亚于功能链路。

## 11. 建议优先落地的 MVP 闭环

为了避免项目长期停留在架构层，建议优先做一个严格收敛的 MVP，而不是一次性打满所有能力。

| 阶段 | MVP 能力 | 暂不做 |
| :--- | :--- | :--- |
| **MVP-1** | 单租户、单模型、单模板沙箱、基础聊天式任务执行 | 多租户套餐、复杂账单、BYOC |
| **MVP-2** | 增加租户配额、任务状态机、SSE 实时回传、基础 Usage Ledger | Stripe 自动出账、复杂税务 |
| **MVP-3** | 增加 OpenMeter、积分扣减、人工确认节点、工具白名单 | 跨区域部署、企业私有云 |
| **MVP-4** | 增加多模型路由、细粒度 RBAC、审计导出、账单同步 Stripe | 完整 BI 体系 |

这一路径的核心思想是：先验证“任务能跑、状态能看、成本能算、权限可控”，再逐步扩展成完整企业平台。

## 12. 结论

现有仓库已经完成了较完整的方案级设计，但距离可实施系统还差最后一段关键工作，即把架构层描述固化为 **服务边界、状态机、事件模型、授权模型、审计链路和补偿机制**。其中最重要的不是继续扩展组件清单，而是尽快把以下五件事落地：第一，明确统一上下文与状态机；第二，建立平台级 Usage Ledger；第三，为 OpenCode 会话与工具调用建立显式授权层；第四，把 E2B 生命周期事件真正纳入可回放账本；第五，将在线控制路径和离线账单路径彻底解耦。

只要这五点做实，平台就会从“架构可讲”进化为“工程可交付”；反之，即便继续增加更多图示、更多模块和更多技术名词，也难以穿透实现层的复杂度。
